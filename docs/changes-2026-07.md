## 1. 사건노트 채점 개편

**상태:** 적용됨 (push 전)
**브랜치:** `fix/scoring`
**대상 파일:** `case-note-similarity.js` 단일

| 커밋 | 내용 |
|---|---|
| `6f2700b` | 유사도 최종 점수의 100점 상한 제거 |
| `72d1aa0` | 오답 지목 시 최종 점수에도 55점 상한 적용 |
| `8b43d74` | 동점 시 사건노트 내용 점수로 순위 결정 |
| `3e14c6b` | 동점 시 등수 번호도 내용 점수로 구분 |

### 배경

2026-07-22 I팀 회의에서 최종 점수 산식을 다음과 같이 정했습니다.

```
최종 점수 = 사건노트 점수 + 남은 질문권 개수
```

목적은 세 가지입니다.

1. **동점 방지** — 백령고 운영 시 동점이 두 쌍 발생해 시상이 애매했음
2. **질문권 지급량 튜닝 부담 제거** — 넉넉히 지급하고 남긴 만큼 점수를 주면, 몇 개를 줘야 적당한지 고민할 필요가 없음
3. **프롬프트 역량 평가** — 적은 질문으로 원하는 답을 얻는 능력을 점수에 반영

코드를 확인한 결과 이 의도가 세 지점에서 막혀 있었습니다.

### 1-1. 100점 상한 제거 (`6f2700b`)

#### 문제

`scoreNote()` 최종 라인에 `Math.min(100, ...)`이 있어 상위권에서 동점이 재발했습니다.

| | 사건노트 점수 | 남은 질문권 | 최종 |
|---|---|---|---|
| A팀 | 95 | 8 | 100 |
| B팀 | 88 | 15 | 100 |

동점을 제거하려고 도입한 규칙이, 정작 시상 대상 구간에서 무력화되는 구조였습니다.

#### 변경

| 위치 | 변경 |
|---|---|
| `:358-361` | `roundScoreUncapped()` 신규 추가 |
| `:444` | `scoreNote()` 최종 점수의 `Math.min(100, ...)` 제거 |
| `:363-366` | `formatScore()` → `roundScoreUncapped` 사용 |
| `:1018` | `animateRevealScore()`의 `Math.min(100, ...)` 제거 |
| `:969` | `revealOrder()` → `roundScoreUncapped` 사용 |

**`roundScoreUncapped`를 새로 만든 이유:**
기존 `roundScore()`가 내부에 `Math.min(100, ...)` 클램프를 갖고 있습니다 (`:353-356`).
최종 라인의 상한만 제거하면 `roundScore`가 다시 100으로 깎아 실질 변화가 없습니다.
기존 `roundScore`는 내용 점수·보정 점수 계산에서 여전히 100 클램프가 필요하므로 손대지 않고, 상한 없는 헬퍼를 별도로 추가했습니다.

**표시 경로 3곳을 함께 고친 이유:**
계산만 고치면 화면에 반영되지 않습니다.

- `formatScore` — 팀 카드, 평균, 랭킹, 리포트 카드, 연출 화면, 애니메이션 종료값, CSV 내보내기가 모두 이 함수를 경유
- `animateRevealScore` — `formatScore`와 별개인 두 번째 클램프. 1위 발표 연출 전용
- `revealOrder` — 저장된 리포트를 다시 읽을 때 재클램프. **정렬 순서까지 영향** (103점과 107점이 둘 다 100이 되어 순위 동점 처리됨)

### 1-2. 오답 지목 시 최종 점수에도 55점 상한 (`72d1aa0`)

#### 문제

`penalty.cap`은 `baseScore`와 `contentScore` 계산에만 적용되고 최종 `score` 라인에는 적용되지 않았습니다.
따라서 오답 지목 팀도 질문권을 많이 남기면 최종 점수가 55를 넘었습니다.

100점 상한이 있을 때는 최대 100까지였으나, 상한 제거 후 무제한이 되어 방치할 수 없게 되었습니다.

| | 사건노트 | 남은 질문권 | 최종 |
|---|---|---|---|
| 범인 **맞힘**, 노트 평범 | 68 | 8 | 76 |
| 범인 **틀림**, 질문 아낌 | 55 (cap) | 25 | 80 |

범인을 틀린 팀이 맞힌 팀을 역전합니다. 게임이 성립하지 않습니다.

#### 변경 — `:443-446`

```js
const totalScore = contentScore + questionCreditBonus.score;
const cappedTotal = penalty.cap < 100 ? Math.min(penalty.cap, totalScore) : totalScore;
```

**`cap < 100` 조건이 반드시 필요합니다.**
`penalty.cap`은 정답 지목 시에도 `100`이라, 무조건 `Math.min(penalty.cap, ...)`을 걸면 정답 팀이 100점에서 잘려 1-1 작업이 무효화됩니다.
이 조건을 "불필요한 분기"로 판단해 제거하지 마십시오.

#### 결과

오답 지목 팀은 질문권을 몇 개 남기든 **최대 55점**입니다.
상한이 이미 사건노트 점수만으로 채워지므로 질문권 보너스가 반영되지 않습니다.

오답 팀이 여럿이면 모두 55점 동점이 됩니다. 시상 대상 구간이 아니므로 허용하기로 했습니다.

### 1-3. 동점 시 내용 점수로 순위 결정 (`8b43d74`)

#### 규칙

최종 점수가 같으면 **사건노트 내용 점수(`contentScore`)가 높은 팀이 상위**.

질문권을 아껴 점수를 올린 팀보다, 사건을 잘 푼 팀이 이기는 것이 게임 취지에 맞다고 판단했습니다.

#### 변경

| 위치 | 변경 |
|---|---|
| `:595-598` | `contentScoreOf` 헬퍼 신규. 값이 없으면 0 |
| `:612-613` | 랭킹 정렬: 최종 점수 → `contentScore` → 입력 순서 |
| `:986-987` | `revealOrder`: 등수 → 최종 점수 → `contentScore` → 이름순 |
| `:728`, `:1167` | 리포트 객체에 `contentScore` 전달 (AI 응답 경로 + 폴백 경로) |

**배선 2줄이 필수였습니다.**
`revealOrder`는 `state.reports`를 정렬하는데, 리포트 객체는 `{name, rank, score, report}` 4개만 담고 있었습니다.
`reportPayload()`에는 `contentScore`가 있으나 리포트 생성 단계에서 버려지고 있었습니다.
정렬 조건만 추가했다면 `undefined - undefined = NaN`이라 무동작이었을 것입니다.

**`contentScoreOf`를 공용 헬퍼로 만든 이유:**
정렬 지점이 세 곳인데 규칙이 갈리면 화면마다 순서가 달라집니다.
새로 정렬 로직을 추가할 때는 반드시 이 헬퍼를 쓰십시오.

### 1-4. 등수 번호도 내용 점수로 구분 (`3e14c6b`)

#### 문제

1-3으로 표시 순서는 갈렸으나 **등수 라벨은 여전히 동점**이었습니다.
90점 두 팀이 위아래로 나뉘어 표시되면서 둘 다 "1위"로 표기·호명되어, 시상이 불가능했습니다.

한쪽만 고치면 랭킹판과 발표 등수가 어긋납니다.

#### 변경

| 위치 | 변경 |

| `:657-672` | `rankedTeams` 동점 판정에 `contentScoreOf` 포함 |

### 운영 파라미터 — 2026-07 기준

코드 변경은 아니지만 채점 설계와 직결됩니다.

| 항목 | 값 |
|---|---|
| 팀당 질문권 지급 | **30개** |
| 질문권 → 점수 배율 | **1:1** |
| 황금열쇠 증감 | ±3개 (6점 스윙) |

**30개로 정한 근거 (백령고 실측):**

- 팀 평균 질문권 사용량 약 14개
- 사건노트 점수 분포 60~80점 (힌트 제공 시)

노트 점수 폭이 약 20점, 질문권 잔량 폭이 약 14점이므로 **노트 점수가 순위를 주도**합니다.

50개 지급을 검토했으나 질문권 폭이 노트 폭을 넘어서, 사건을 더 잘 푼 팀이 지는 역전 현상이 발생합니다.

| 50개 지급 시 | 사건노트 | 남은 질문권 | 최종 |
|---|---|---|---|
| A팀 — 효율적 | 82 | 30 | **112** |
| B팀 — 꼼꼼하나 비효율 | 90 | 15 | **105** |

노트는 B팀이 8점 높으나 최종은 A팀이 7점 높습니다.
**질문권 지급량을 늘릴 경우 배율을 0.5로 낮추는 검토가 필요합니다.** (`questionCreditBonusFor` 한 곳 수정)

30개 지급을 전제로 배율 1:1을 유지하고 있으므로, 지급량 변경 시 이 문서를 함께 갱신해 주십시오.

### 미해결 — 게임팀 확인 요청

#### (A) 오답 지목 페널티의 비대칭

정답과 오답을 함께 적으면 상한이 적용되지 않습니다.

| 작성 방식 | 범인 지목 점수 | 상한 |
|---|---|---|
| "범인은 강우진이다" | 16 | 없음 |
| "범인은 강우진이다. 서하린도 범인이다" | 16 − 5 = 11 | 없음 |
| "범인은 서하린이다" | 0 | **55** |

`wrongCulpritPenalty()`(`:342-351`)는 강우진이 함께 언급되면 `cap: 100` + `-5점`으로,
언급되지 않으면 `cap: 55`로 처리합니다.

확신한 팀 입장에서는 양다리가 5점 손해이므로 유리하지 않습니다.
다만 **확신이 없는 팀에게는 5점을 지불하고 45점 위험을 회피하는 선택지**가 됩니다.

원 저장소의 기존 동작이며 중학생이 이를 계산해 활용할 가능성은 낮다고 보아 변경하지 않았습니다.
페널티 폭을 조정하려면 `:346` 부근의 감점값을 바꾸면 됩니다.

#### (B) 질문권 자체에 상한이 없음

`cleanRemainingCredits`(`:181-185`)는 하한 0만 적용하고 상한이 없습니다.
질문권이 곧 점수이므로 이론상 점수도 무제한입니다.

황금열쇠 칸으로 획득한 질문권도 그대로 점수가 되므로, 주사위 운이 점수에 반영됩니다.
현재 설계(30개 지급, ±3개 증감)에서는 6점 스윙으로 노트 점수 폭(20점) 안에 들어와 허용 가능하다고 판단했습니다.

**황금열쇠 증감 폭을 키울 경우 재검토가 필요합니다.**

#### (D) 점수에 소수점이 발생하는 원인 — 구체성 보정

`specificityBonus()`(`:381-396`)가 최대 **+0.9점**을 더합니다.

| 조건 | 가산 |
|---|---|
| 90자 이상 | +0.2 |
| 180자 이상 | +0.2 |
| 8자 이상 문장 2개 이상 | +0.1 |
| 구체어 12종(강우진·교무실·CCTV·6시15분·주체성 등) 매칭 | 개당 +0.05, 최대 +0.4 |

이것이 최종 점수에 소수점 첫째 자리를 만드는 유일한 원인입니다.

원래는 미세 동점을 가르는 장치였으나, 1-3·1-4에서 `contentScore` 기준 동점 처리가 도입되어 **역할이 상당 부분 중복**됩니다.

정수 표시를 원할 경우 선택지:

- **표시만 반올림** — 계산은 유지하고 화면·CSV만 정수로. 순위 판정에는 여전히 소수점이 쓰임
- **`specificityBonus` 제거** — 계산 자체를 정수화. 길이·구체성 보상이 사라짐

전자가 안전합니다. 후자는 채점 기준 변경이므로 게임팀 합의가 필요합니다.

#### (E) 뺏기 규칙의 예외 처리

황금열쇠로 다른 팀의 질문권을 뺏을 때, 대상 팀의 잔량이 부족한 경우의 처리가 정해지지 않았습니다.
코드상 0 미만으로는 내려가지 않으나, **게임 규칙 차원의 결정이 필요합니다.**
(그냥 넘어갈지 / 다른 팀에서 뺏을지 / 남은 만큼만 뺏을지)

## 3. 질문권 이상 증가 조사

**상태:** 조사 중. 원인 미확정

### 사건

질문권 목표치를 10개로 잡고 9턴 진행 후 교사가 3~4개를 추가 지급했으나, 일부 팀 기기에서 **19~20개**로 관측되었습니다.

당시 교사 화면의 접속자 목록이 간헐적으로 사라졌다 나타나는 현상도 함께 보고되었습니다.

**이 문제는 채점 개편 이후 중요도가 올라갔습니다.** 남은 질문권이 곧 점수이므로, 6~7개 차이는 6~7점 차이이며 사건노트 점수 폭(약 20점)과 비교해 순위를 뒤집을 수 있는 크기입니다.

### 확인된 사실

- `/api/status` 응답에서 `hasCreditStore: true` — Upstash는 설정되어 있음
- 두 반은 서로 다른 기기를 사용했으며 세션 중 로그아웃은 없었음

### 원인 후보 (미확정)

#### (A) 교사 지급 중복 클릭

2번 항목에서 수정 완료. 3~4개 × 2 = 6~8개로 관측치와 일치합니다.
가장 유력하나 확증은 없습니다.

#### (B) 학생 반 구분 폴백

반은 로그인 화면의 선택 버튼으로만 정해지며, 다음 순서로 폴백합니다.

```

          → localStorage["kit-last-class-section"]
          → "class-a"
```

교사 계정은 `lockedClassIdForRequest`(`api/_credits.js:92-98`)로 `master`→`class-a`, `master2`→`class-b`가 강제되어 클라이언트 값이 무시되지만, **학생은 `guardPage()`의 반 재고정 대상이 아닙니다** (`auth.js:355` `if (account?.classId)`).

두 반이 팀 이름 8개를 공유하므로(`api/_credits.js:3`), 반이 틀리면 다른 반의 동명 팀에 **정확히 겹쳐 합산**됩니다.

학생이 스스로 얻는 질문권은 증거 코드 +1, 윤리 퀴즈 +1뿐이므로 한 차시 누적이 6~7개 범위입니다. 관측치와 부합합니다.

> ⚠️ `normalizeClassId`(`api/_credits.js:60-66`)의 마지막 줄은 알 수 없는 값을 거부하지 않고 그 문자열 자체를 새 반으로 사용합니다. 오타 `clas-b`를 보내면 `clas-b`라는 유령 반이 생기고 데이터가 조용히 그쪽으로 갑니다.

#### (C) 질문 실패 환불

`api/chat.js:119-127` `refundCredit`이 OpenAI 호출 실패 시 차감분을 되돌립니다.
당시 연결 불안정이 잦았다는 보고가 있어, 차감과 환불의 정합성 확인이 필요합니다.

새 정렬 로직을 추가할 때 직접 `a.contentScore - b.contentScore`를 쓰지 말고 `contentScoreOf` 헬퍼를 사용하십시오.

`auth.js:3-14`에 계정·비밀번호가 평문 하드코딩되어 있고 `DEPLOYMENT.md:90-101`에도 기재되어 있습니다.

다만 저장소를 public으로 전환할 경우 재검토가 필요합니다.

### 저장소 구조

- 관계형 DB 없음. Upstash Redis를 KV로 사용하며, 미설정 시 서버 메모리로 대체됩니다
- 메모리 대체 시 **Vercel 다중 인스턴스 환경에서 데이터가 유실됩니다** (`api/_credits.js:179-181`)
- 두 기기 간 상태를 주고받는 기능(승인·전달 등)을 새로 만들 경우 **Upstash 설정이 전제 조건**입니다
- 채점 결과는 브라우저 localStorage에만 저장됩니다. 브라우저가 바뀌면 초기화됩니다
- `.env.example`이 없습니다. 환경변수는 `DEPLOYMENT.md`에 서술형으로만 정리되어 있습니다
